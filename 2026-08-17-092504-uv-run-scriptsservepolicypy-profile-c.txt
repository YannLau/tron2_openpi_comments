● 问题已定位并修复。总结如下：

  结论：不是脚本逻辑问题，是 XLA GPU 编译器段错误

  进程退出码是 139（SIGSEGV），崩溃点在你的"执行点2"——warmup 的 policy.infer()
  触发 JIT 编译时，jax._src.compiler.backend_compile 里
  segfault，所以服务器从未真正启动就被杀掉了。

  根因

  venv 里的 CUDA 工具链版本错配：

  1. 主因：jax 固定为 0.5.3（2025 年 3 月），但 torch 2.7.1 硬性要求 cuDNN
  9.5.1.17，被解析器装进了同一个 venv。jaxlib 0.5.3 的 XLA 在做 GPU kernel
  autotune（枚举候选卷积/GEMM 内核）时与 cuDNN 9.5
  不兼容直接段错误。我用最小复现验证过：裸 lax.conv_general_dilated 一行 JIT 
  就崩，而 matmul（走 cuBLAS 不参与 autotune）没事。
  2. 次因：~/.bashrc 里 LD_LIBRARY_PATH=/usr/local/cuda-12.8/lib64 + CUDA_HOME
  把系统 CUDA 12.8 库混进了 jax 进程；以及 jax-cuda12-plugin 0.5.3 对 ptxas 只有
  >=12.6.85 无上限，uv 解析到了 12.9.41（比 XLA 0.5.3 新太多）。

  已做的修复（两处）

  1. scripts/serve_policy.py:9 — 在 import jax 之前自动设置（用户自己设了
  XLA_FLAGS 则不覆盖）：
  if "--xla_gpu_autotune_level" not in os.environ.get("XLA_FLAGS", ""):
      os.environ["XLA_FLAGS"] = (
          os.environ.get("XLA_FLAGS", "") + " --xla_gpu_autotune_level=0"
      ).strip()
  关闭 autotune 后 XLA 用确定性启发式选 kernel，不再枚举候选 →
  不崩。放在脚本里可以同时覆盖 Docker/compose 启动路径。

  2. pyproject.toml — 固定 nvidia-cuda-nvcc-cu12==12.6.85（已 uv sync 更新
  uv.lock），防止下次同步又把 ptxas 升回 12.9.41。
